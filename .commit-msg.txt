Phase 2.8: Editor integration — RoadViewport uses buildRoad() pipeline

Replaces the TypeScript mesh-building code in RoadViewport.tsx with
the C++ buildRoad() output. The 3D viewport now uploads typed arrays
from the lane engine directly to Babylon.js GPU buffers.

Changes to RoadViewport.tsx:
  - Added buildCacheRef (Map<string, RoadBuildResult>) alongside
    the existing sampleCacheRef
  - refreshSampleCache() now calls both sampleCenterline() (for 2D)
    and buildRoad() (for 3D) per road
  - update3DMeshes() now checks for cached buildRoad() result first:
    - If available: uploads Float32Array/Uint32Array directly to
      Babylon VertexData (with Y/Z swap for Babylon's Y-up system)
    - If not available: falls back to legacy TS mesh building
  - Materials mapped from C++ section types:
    - asphalt → asphalt texture, pickable
    - yellow_marking → yellow dashed center, not pickable
    - white_marking → white edge/divider, not pickable
  - Curbs and sidewalks still generated in TS (Phase 2 doesn't
    generate those yet — they use the sample cache)
  - Control point meshes unchanged
  - Intersection surfaces unchanged (Phase 3 territory)
  - Legacy buildDashedMarking extracted to module-level function
    for fallback path

Verified in Electron:
  - Native addon loads correctly (ABI 146 for Electron 42.5.1)
  - buildRoad() called for each road in the project
  - Mesh sizes: 224-876 vertices per road (adaptive sampling)
  - Intersection detection still works (60 polygon pts, 4 approaches)
  - Split roads after intersection are rebuilt with buildRoad()

No regression: 141 vitest + 463 doctest all pass.
TypeScript build: clean. Vite build: clean.
